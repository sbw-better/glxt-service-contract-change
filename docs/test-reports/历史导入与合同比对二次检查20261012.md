本轮在上一轮6项逻辑修复的基础上，继续检查控制表异常状态、同版本查重、索引数量完整性、事务归属以及SFTP等待边界。分析日志标签字段保持VARCHAR2(1000)，没有新增数据库结构调整。

## 新确认的问题与修复

| 问题 | 具体影响 | 修复 |
|---|---|---|
| 同版本已有样本维度异常被当作停用重启 | 异常数据可能通过重新向量化被静默覆盖 | 查重记录必须匹配当前版本／维度，生效状态只能0或1，标签必须规范；异常整批409，不调用模型、不写样本 |
| 同Hash多行查重结果被Map覆盖 | 缺少唯一约束或异常数据时，任意一条记录可能掩盖标签冲突 | 同批查重发现重复Hash立即拒绝，不选择任意一行 |
| 按维度过滤隐藏异常有效记录 | 有历史记录却可能显示EMPTY，compare按正常空库处理 | 比较当前版本有效总数与实际加载数量；被维度过滤的记录计入errorCount，标记DEGRADED；无可用样本时禁用识别 |
| 控制行状态不一致仍可能允许识别 | 人工建表遗漏约束时，空状态或错误字段组合未被统一拒绝 | Java统一校验模型身份、revision、状态、operationId和expectedSamples；占用／恢复拒绝异常，预测503 |
| 增量提交仅核对操作ID和revision | 对应控制行已进入DB_COMMITTED时仍可能先调用持久化 | 写样本前要求合法控制行且状态RUNNING；不符合条件立即409 |
| DB_COMMITTED恢复可被null参数降级 | 内部调用漏传预期数时可能跳过严格完整性检查 | 恢复预期数量始终取持久化EXPECTED_SAMPLES，不能由调用方参数绕过 |
