## 当前正式业务入口

基础路径：`/glxt-service-contract-change/service/contract-compare`

### POST /compare

请求体必须明确提供：

- `userId`：操作用户，同时透传给 Embedding 网关。
- `instId`：流程实例 ID，仅用于关联和入库。
- `analysisType`：必须明确为 `DOUBLE_VERSION` 或 `CHANGE_DOCUMENT`，不再默认为双版本。
- 双版本提供 `oldFileGetPath`、`newFileGetPath`。
- 单文件提供 `changeFileGetPath`。

双版本示例：

```json
{
  "instId": 10001,
  "userId": "employee-001",
  "analysisType": "DOUBLE_VERSION",
  "oldFileGetPath": "/合同目录/修改前.docx",
  "newFileGetPath": "/合同目录/修改后.docx"
}
```

成功响应只包含：

```json
{
  "analysisId": "4bb11fc4b6b945efaf992fc5eb32fd71",
  "fileChangeTypeCodes": ["04", "19"],
  "analysisStatus": "SUCCESS"
}
```

状态规则：

- `SUCCESS`：没有 `FAILED` 或 `SKIPPED_TOO_LONG` 的变化段落。无变化、全部无可靠匹配也是成功，类型集合为 `[]`。
- `PARTIAL_SUCCESS`：存在预测失败或超长跳过，成功段落仍参与文件级聚合。
- 文件处理、结构解析、PROCESSING 主记录创建或最终事务保存失败时，不返回成功数据。

### POST /export

这是保留的临时导出接口：

- Controller 保持 `void + HttpServletResponse`。
- 不要求 `userId`、`instId`。
- 为兼容旧调用，`analysisType` 未传时仍按 `DOUBLE_VERSION`。
- 不调用 Embedding 或历史向量索引，不写分析日志。
- 双版本 SIMPLE 9 列、CONTEXT 11 列；单文件 8 列，格式不增加预测字段。

## /compare 业务流程

1. 校验请求体元数据和当前分析类型所需文件路径。
2. 生成 `analysisId`，在独立短事务中创建 `PROCESSING` 主记录；失败则立即终止。
3. 通过 `ContractChangeExtractorRegistry` 按 `analysisType` 选择策略：
   - `DoubleVersionChangeExtractor`：校验双版本文件路径，完成 SFTP 下载、Aspose 比较、结构解析和条款差异。
   - `ChangeDocumentExtractor`：校验单文件路径，完成 SFTP 下载和变更内容提取。
4. 策略统一返回完整、未裁剪的 `ContractCompareResponse`。
5. `ContractComparePredictionService` 执行唯一一套段落预测、上下文兜底和文件级聚合：
   - 新增/修改使用 `newContent`，删除使用 `oldContent`。
   - 仅段落结果为 `NO_RELIABLE_MATCH` 时使用上下文。
   - 上下文结果最高为 `CANDIDATE`。
   - 相同规范化文本去重后批量调用，局部模型批次失败按段落降级。
   - HIGH 直接进入文件级集合；CANDIDATE 需两个不同规范化段落共同支持。
6. 计算 `SUCCESS` 或 `PARTIAL_SUCCESS`，序列化完整详细结果。
7. 在一个事务中写入所有段落、Top-K 匹配证据、`RESULT_JSON` 并更新主记录；任一步失败整体回滚。
8. 最终事务失败后，在独立短事务中将主记录更新为 `FAILED`。
9. 数据完整落库后返回精简响应。

## 数据库设计

增量脚本：`database/oracle/02_analysis_log.sql`

- `HT_ANALYSIS_LOG`：分析主记录、流程和用户、文件来源、状态、耗时、模型信息、聚合编码、错误及完整 `RESULT_JSON`。
- `HT_ANALYSIS_PARA_LOG`：条款编号/标题/上级条款、单文件来源标题/目标条款、旧新段落、实际预测文本、状态、输入范围、相似度和类型编码。
- `HT_ANALYSIS_MATCH_LOG`：每个变化段落的 Top-K 历史样本、相似度、类型编码和排名。

三表不建立物理外键。原因是它们属于分析审计数据，需要支持独立归档和清理；历史样本也可能失效或删除。数据一致性由以下机制保证：

- 主表 `ANALYSIS_ID` 唯一。
- 段落表 `(ANALYSIS_ID, PARAGRAPH_ID)` 唯一。
- 匹配表 `(PARAGRAPH_LOG_ID, RANK_NO)` 唯一。
- 明细与最终主表更新在同一个事务中执行。
- 每次 Mapper 写入必须恰好影响一行，否则抛错回滚。

`01_schema.sql` 只保留历史向量库基础表；存量环境按顺序执行 `01_schema.sql`（如尚未初始化）和增量 `02_analysis_log.sql`。

## 代码结构边界

- `ContractChangeAnalysisService` 只负责编排、状态、序列化和调用事务持久化。
- `AnalysisResultPersistenceService` 统一三个 Mapper 的事务写入，不保留仅包装 Mapper 的多个日志 Service。
- `ContractCompareService` 只服务详细比较和 Excel 导出，不执行向量预测。
- 策略类只负责自身请求校验和从对应文件形态生成详细变化结果，不复制预测、聚合和持久化逻辑。
- 本期不提供分析日志查询接口；完整 JSON 已保存，可在后续有明确查询条件时实现。
- 未经人工确认的预测不会写入历史向量库，历史样本继续通过现有 Excel 导入流程维护。
- 不为未来需求预建审核任务、确认回写、无调用查询或重复 DTO。

## 当前验收重点

- /compare 不接受请求头 UserId 替代请求体 userId。
- /compare 缺少 instId 或 analysisType 时返回业务码 400。
- /export 未传 userId、instId、analysisType 时仍可按旧双版本方式导出。
- SUCCESS 响应中的 analysisId 必须已存在完整结果。
- 详细 JSON 保留条款上下文、changeDetails、段落预测、warnings、predictionSummary 和 fileChangeTypeCodes。
- 最终明细任一写入失败时事务回滚并标记主记录 FAILED。
- /export 不触发向量预测，原 Excel 列保持不变。
